# REPORT: аудит продуктивності «Каталог репетиторів»

## 1. Умови вимірювання

- MacBook (Apple M4, 16 GB), macOS; Chrome 157.0.8103.51, інкогніто
- Збірка: `npm run build` + `npm run preview` (порт 4173)
- Performance: CPU 4× slowdown, Fast 4G, Disable cache; Lighthouse: mobile
- Кожна цифра «ДО» і «ПІСЛЯ» для трейсів: медіана з 3 запусків (трейси в `report/`)
- «Найдовша задача» = найдовший `RunTask` на main thread за запис; long task = задача > 50 мс

## 3. Виправлення

| Коміт | Проблема за сценарієм | Причина | Виправлення | Результат «до → після» |
|---|---|---|---|---|
| `perf(useBioClamp): remove layout thrashing and throttle scroll via rAF` (775e661) | Сортування, пошук, скрол: сторінка підвисає на 1–3 с, у Bottom-Up `getBoundingClientRect` займає найбільше часу. | Хук для кожної картки чергував запис класу й читання `offsetHeight`, тож кожне читання змушувало браузер перераховувати layout. Подію `scroll` обробляли без обмеження частоти. | Спочатку всі читання, потім усі записи. `scroll` обробляється через `requestAnimationFrame`. | `getBoundingClientRect`: сортування 1 777 → 25 мс, пошук 814 → 25 мс |
| `perf(App,TutorList,TutorCard): memoize visible list and cards, stabilize callbacks` (9380ab5, 1485547) | Відкриття й закриття картки: React Profiler показує коміт 200–1 500 мс, причина «App», перерендерюються всі картки. | `getVisibleTutors` викликався на кожен рендер без `useMemo`, `TutorCard` був без `memo`, а нові inline-колбеки робили props завжди різними. | `useMemo` для списку, `useCallback` для обробників, стабільні props, `memo(TutorCard)`. | Коміти Profiler 201–1 507 → 6–14 мс; компонентів у коміті 673–4 005 → 7–17 |
| `perf(search): cache normalized haystack and query, defer query updates` (eb85b4c) | Пошук «Хімія»: поле лагає, найдовша задача 1,6 с. | `normalizeText` (NFD і 2 regex) виконувався для тексту кожного з 2000 репетиторів на кожну літеру, а запит нормалізувався знову для кожного. | Кеш нормалізованого тексту в `WeakMap`, запит нормалізується один раз, `useDeferredValue`. | 1 631 → 43,8 мс (разом з іншими виправленнями) |
| `perf(sort): compute tutorScore once per tutor` (8712010) | Сортування «Рекомендовані»: найдовша задача 3 с. | Компаратор викликав `tutorScore` ≈ 40 тис. разів, кожен раз розбираючи ~23 дати. | Оцінка рахується один раз на репетитора й кешується. | 2 980 → 55,8 мс (разом з іншими виправленнями) |
| `perf(images): lazy-load card photos, reserve space, prioritize and shrink hero` (6a60d9b), `perf(images): convert photos to resized JPEG` (847cf4a) | Завантаження: LCP 27 с (елемент `img.hero__image`), 23 МБ на сторінку, CLS 0,22. | Hero 1,3 МБ і 36 фото по ~600 кБ вантажилися одразу, усі завеликі для показу. `<img>` без розмірів, тому сторінка стрибала. | PNG → JPEG (фото 400 px, hero 1600 px), `loading="lazy"`, `width/height`, `aspect-ratio`. | 41 → 12 запитів; 23,0 МБ → 183 кБ; hero 1 317 → 48 кБ |
| `perf(list): render cards progressively` (hash: _додати_) | Завантаження: TBT 2 950 мс, Lighthouse 46. | На старті монтувалося 2000 карток (~60 тис. DOM-вузлів). | Спочатку 24 картки, решта підвантажується через `IntersectionObserver`; пошук, фільтри й сортування працюють по всьому списку. | TBT 2 950 → 10 мс; Lighthouse 46 → 98 |

**Експеримент без коміту.** `<link rel="preload">` для hero погіршив FCP з 1,2 до 5,9 с, Lighthouse 46 → 30. Причина: важкий hero йшов першим, перед JS і CSS. Preload прибрано.

Колонку «Результат» залишив, бо лабораторна вимагає цифри до і після для кожного виправлення. Якщо захочете рівно три колонки, її можна просто видалити.
